การเพิ่มเกม: ลำดับเรียกจริง
  1. ผู้ใช้กรอกฟอร์ม → validator ตรวจข้อมูล
  2. GameEditorPage._save() สร้าง SteamGame แล้วเรียก repository
  3. Repository หา UID + ID token แล้วเลือก POST (ใหม่) หรือ PUT (แก้)
  4. API ตรวจ token/ข้อมูล และเขียน Firestore
  5. เมื่อ API ตอบสำเร็จ Repository ค่อย upsert SQLite แล้วคืน model
  6. หน้าฟอร์ม pop กลับ; stream/query ส่งข้อมูลใหม่ให้ list
Future<SteamGame> saveGame(SteamGame game) async {
  final userId = _userId; // UID จาก FirebaseAuth.currentUser
  final saved = game.copyWith(
    id: game.id ?? _games.doc().id, // ใช้ id เดิมหรือสร้าง id ใหม่
    userId: userId,
  );
  final token = await _idToken; // Firebase ID token ของ session นี้

  // เลือก method ตามว่ามี id เดิมหรือไม่
  final remote = game.id == null
      ? await _api.createGame(saved, token)
      : await _api.updateGame(saved, token);

  // เขียน SQLite หลัง Cloud/API สำเร็จเท่านั้น
  await _database.saveGame(remote.copyWith(userId: userId));
  return remote.copyWith(userId: userId);
}

อ้างอิง: lib/services/firestore_game_repository.dart (saveGame); client methods อยู่ใน lib/services/favorites_api_service.dart

  • UI/Page: รับ input แสดงสถานะและเรียก repository/service
  • Model: รูปแบบข้อมูลเกมที่ทุกชั้นใช้ร่วมกัน
  • Repository: รวมการอ่าน/เขียน/ลบ และซ่อนรายละเอียด data source จาก UI
  • Service: จัดการ HTTP, token, JSON, timeout และ error
  • Database adapter: เก็บสำเนาในเครื่องตาม platform
อธิบายให้ตรง: SQLite ในเวอร์ชันนี้เป็น local cache/mirror ไม่ใช่ offline-first source of truth; การเขียนส่ง API ก่อน แล้วค่อยเขียน SQLite เมื่อสำเร็จ ถ้าไม่มีเน็ตการเพิ่ม/แก้/ลบจะไม่ถูกเข้าคิว
ลำดับตอนเปิดหน้ารายการ (watchGames)
1 · อ่าน SQLite→2 · yield ให้ UI เห็นรายการเร็ว→3 · GET API เมื่อออนไลน์→4 · replace local cache→5 · ฟัง Firestore snapshots→6 · sync cache และ yield รอบใหม่

ถ้า API ดึงไม่สำเร็จ catch ไว้เพื่อให้มีโอกาสแสดง cache ต่อ แต่การเขียนแบบ offline queue ยังไม่มี

Future<void> _save() async {
  // หยุดถ้ากำลังบันทึก หรือข้อมูลไม่ผ่าน validator
  if (_saving || !_formKey.currentState!.validate()) return;
  setState(() { _saving = true; _error = null; });

  try {
    final saved = await widget.repository.saveGame(
      SteamGame(
        id: widget.game?.id, // มี id = edit; null = create
        appId: _appId.text.trim(),
        title: _title.text.trim(),
        description: _description.text.trim(),
        date: _date,
        mood: _genre,
        genre: _genre,
        imageUrl: _image.text.trim(),
        rating: _rating,
        isFavorite: _isFavorite,
      ),
    );
    // หลัง await อาจปิดหน้าไปแล้ว จึงเช็ก mounted ก่อนใช้ context
    if (mounted) Navigator.pop(context, saved);
  } catch (_) {
    if (mounted) setState(() {
      _saving = false;
      _error = 'บันทึกไม่สำเร็จ กรุณาลองใหม่';
    });
  }
}

    {String? body, Uri? uri}) => _client
  .send(http.Request(method, uri ?? Uri.parse(endpoint))
    ..headers.addAll({

      'Content-Type': 'application/json',

  .then(http.Response.fromStream)

08 · AUTH + CLOUD SECURITY

Login, Firestore และ Rules

Firebase Authentication จัดการสมัคร/เข้าสู่ระบบ; UID ระบุเจ้าของ; ID token ใช้ยืนยัน request; Firestore เก็บเกม; Rules บังคับสิทธิ์ที่ฝั่งบริการ ไม่ใช่แค่ซ่อนรายการในหน้าจอ

  // resource คือ document ปัจจุบันที่กำลังอ่าน/แก้/ลบ
  return request.auth != null
      && resource.data.userId == request.auth.uid;
}
function ownsIncomingGame() {
  // request.resource คือข้อมูลใหม่ที่กำลังจะเขียน
  return request.auth != null
      && request.resource.data.userId == request.auth.uid;
}

allow read, delete: if ownsExistingGame();
allow update: if ownsExistingGame()

อ้างอิง: firestore.rules (ownership, validation, default deny)

  • create: ผู้ใช้ต้องล็อกอินและ owner ของข้อมูลใหม่ต้องตรง UID
  • read/delete: ต้องเป็นเจ้าของ document เดิม
  • update: ตรวจ owner เดิมและ owner ใหม่ ป้องกันโอน document
  • validGame: ตรวจ keys, ความยาว title/description/image, ช่วง rating และชนิด boolean
  • default deny: path อื่นทั้งหมดไม่อนุญาต
ข้อควรพูดอย่างแม่น: server อ่าน claim จาก token เพื่อได้ UID และส่ง token ต่อให้ Firestore; การ decode JWT payload อย่างเดียวไม่ใช่การ verify signature แต่ Firestore ต้องตรวจ token และบังคับ Rules อีกชั้น ควรสาธิตด้วยบัญชีสองคนจริง

12 · ORAL EXAM

ชุดคำถาม–คำตอบสำหรับอ่านสอบ

คำตอบเป็นแกนสั้น ๆ สำหรับจำ ให้ขยายด้วยการชี้ไฟล์/สาธิต และใช้คำพูดของตัวเอง

1. แอปนี้ทำอะไร?

จัดเก็บเกม Steam ที่ชอบในบัญชีส่วนตัว เพิ่มรายละเอียด หมวด คะแนน และรูป ดูเกมแนะนำ/ชุมชน และสรุปสถิติ

2. ทำไมเป็น StatefulWidget?

เพราะหน้ามีข้อมูลเปลี่ยนตาม interaction เช่น tab, form, filter, loading และ favorite; setState ทำให้ UI rebuild

3. Model มีประโยชน์อย่างไร?

กำหนด field/type ให้ชัดและรวมการแปลง JSON/Map/Firestore ไว้ ไม่ต้องส่ง map ดิบไปทุก widget

4. ทำไมแยก toMap กับ toJson?

SQLite เก็บ boolean เป็น 0/1 แต่ JSON/Firestore เก็บ boolean จริง จึงต้อง serialize ให้ตรงชนิดปลายทาง

5. validator คืนค่าอะไร?

คืนข้อความเมื่อไม่ผ่าน และคืน null เมื่อผ่าน; save จะหยุดก่อนเรียก repository หาก validation ไม่ผ่าน

6. รู้ได้อย่างไรว่าเป็น Create หรือ Update?

ไม่มี id คือรายการใหม่; มี id เดิมคือแก้ record เดิมและส่ง PUT

7. Navigator.push ทำอะไร?

เพิ่มหน้าใหม่บน navigation stack; MaterialPageRoute สร้างหน้าและส่ง model ผ่าน constructor

8. mounted ใช้ทำไมหลัง await?

ป้องกัน setState หรือใช้ context หลังหน้าถูก dispose ขณะรอ network

9. SQLite มีจริงไหม?

มี mobile adapter ใช้ sqflite สร้าง steam_favorites.db และ steam_games table; save/replace/delete ทำผ่าน repository เมื่อ remote สำเร็จ

10. SQLite เป็น source of truth หรือไม่?

ไม่ใช่ใน implementation ปัจจุบัน เป็น local mirror/cache; REST/Firestore เป็นทางเขียนหลัก

11. ปิดแอปแล้ว SQLite ยังอยู่ไหม?

ข้อมูลที่เขียนลง SQLite สำเร็จยังอยู่ในเครื่องหลังปิดแอป; การถอนแอป/ล้างข้อมูลแอปอาจลบฐานข้อมูลในเครื่อง

12. ออฟไลน์เพิ่มเกมได้ไหม?

ไม่ได้ใน flow ปัจจุบัน เพราะเรียก API ก่อน; cache เอาไว้แสดงข้อมูลที่เคยโหลด ไม่ได้ queue การเขียน

13. ทำไมเริ่มอ่านจาก cache?

ให้แสดงข้อมูลเดิมได้เร็ว ก่อนดึงข้อมูลล่าสุดจาก Cloud มาปรับ cache แล้วส่ง stream update ให้ UI

14. FutureBuilder ช่วยอะไร?

จัด UI ตาม Future ที่ยังรอ, สำเร็จ, error; โค้ดแยก empty list ออกจาก error และมี retry

15. ทำไมเก็บ Future ไว้ใน State?

ป้องกันยิง HTTP ซ้ำทุก rebuild; สร้าง Future ใหม่เมื่อ refresh/retry

16. GET/POST/PUT/DELETE ต่างกันอย่างไร?

อ่าน/สร้าง/แก้/ลบตามลำดับ เป็น HTTP methods ที่ REST handler แยกจัดการ

17. API error แล้วแอปจัดการอย่างไร?

service ตรวจ status/JSON และ timeout แล้วโยน exception; UI แสดง error state กับวิธีลองใหม่แทน crash

18. Firebase Auth กับ Firestore ทำหน้าที่อะไร?

Auth ยืนยันตัวตน; Firestore เก็บข้อมูลเกมใน Cloud; UID ผูก document กับผู้ใช้

19. ID token อยู่ตรงไหนใน REST?

อยู่ใน Authorization: Bearer header ของ request favorites เพื่อยืนยัน session

20. Rules ป้องกันข้อมูลข้าม user อย่างไร?

request.auth.uid ต้องตรง userId; read/delete ตรวจข้อมูลเดิม ส่วน create/update ตรวจข้อมูลใหม่ด้วย

21. ทำไม update ตรวจ owner เดิมและใหม่?

ยืนยันว่าคนเดิมเป็นเจ้าของ และข้อมูลใหม่ยังเป็นของคนเดิม ป้องกันเปลี่ยน owner

22. client filter แทน Security Rules ได้ไหม?

ไม่ได้; client ถูกแก้หรือเรียก API ตรงได้ ต้องบังคับสิทธิ์ฝั่ง server/Firestore

23. API handler decode token ปลอดภัยพอไหม?

การ decode claim อย่างเดียวไม่ verify ลายเซ็น; handler ส่ง token ต่อไป Firestore ซึ่งต้องตรวจ token/Rules จริง และควรทดสอบด้วย token ของ user ที่ถูกต้อง

24. Firebase API key เป็น password ไหม?

ไม่ใช่ service-account secret; แต่ต้องตั้ง Rules ให้ปลอดภัย และห้ามเปิดเผย password, user ID token หรือ private key

25. Empty state ต่างจาก error อย่างไร?

empty คือโหลดสำเร็จแต่ไม่มีข้อมูล; error คือโหลดไม่สำเร็จ ต้องแสดงข้อความและปุ่มที่เหมาะกับแต่ละสถานะ

26. รูปภาพพังแล้วเกิดอะไร?

GameArtwork ใช้ placeholder/loading และ error fallback แทนการปล่อยภาพเสียหรือทำให้หน้า crash

27. บีบอัดภาพอย่างไร?

อ่าน orientation, ย่อความยาวด้านภาพเป็นขั้น และลอง JPEG quality หลายระดับจนต่ำกว่าขนาดเป้าหมาย 250 KB

28. ค้นหาและ filter ทำงานอย่างไร?

กรอง list ด้วย genre, favorite และข้อความ title แบบ lowercase; เงื่อนไขต้องผ่านทั้งหมด

29. กราฟสถิติมาจากไหน?

นับเกมจาก list ปัจจุบัน แบ่งตาม genre และนับ favorite; สีใช้ modulo เพื่อวนซ้ำเมื่อมีหลายหมวด

30. ทำไม adapter ของเว็บต่างจาก mobile?

platform มี API/plugin ต่างกัน; conditional import ให้ใช้ interface เดียว แต่เลือก storage implementation ที่รองรับ

31. ทำอย่างไรให้ข้อมูลแยก user พิสูจน์ได้?

ล็อกอินบัญชี A เพิ่มเกม แล้ว logout ไป B ตรวจว่าไม่เห็น; ตรวจ owner ใน Firestore และลอง Rules/endpoint ด้วย token ของแต่ละบัญชี

32. จะทดสอบ API เมื่อไม่มีเน็ตอย่างไร?

ปิดเน็ตแล้ว refresh หน้า API ต้องขึ้น error/retry ไม่ crash; เปิดเน็ตกลับแล้ว retry ต้องโหลดได้

33. มี automated tests อะไร?

api_test, lab2_test และ widget_test ครอบคลุมบาง UI/CRUD; ยังต้องทดสอบ Auth, Rules, deployment และอุปกรณ์จริงแยก

34. ท้าทายข้อท2 ทำตรงตาม Image.network ไหม?

ใช้ Image กับ NetworkImage และ loading/error builders ซึ่งให้ behavior เดียวกัน แต่ไม่ได้เรียก Image.network constructor ตรงตัว จึงควรชี้แจงตามจริง

35. Bonus ที่ทำคืออะไร?

เลือกรูปจากคลังหรือกล้องและบีบอัดก่อนแนบกับเกม; สาธิต permission และการบันทึกจริง

36. ข้อจำกัดหลักของระบบ?

เพิ่ม/แก้/ลบต้อง online; SQLite เป็น cache; รูปมีเพดานขนาด; API และ Rules ต้อง deploy/config ถูกต้อง

37. จะพัฒนาต่ออะไร?

เพิ่ม offline write queue และ conflict policy, upload รูปไป object storage, verify token ด้วย middleware ที่เชื่อถือได้ และ integration test กับ Firebase Emulator

38. ถ้าถามคะแนนเต็มไหมควรตอบอย่างไร?

ชี้หลักฐานตาม rubric และผลทดสอบจริง อย่ารับประกันคะแนนแทนอาจารย์; เน้นว่าพร้อมเปิด APK, CRUD, API, account isolation, Rules และฟีเจอร์เสริมให้ตรวจ
