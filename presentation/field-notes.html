01 · อ่านหน้านี้ก่อน

ภาพรวมใน 60 วินาที

Steam Favorite เป็นแอป Flutter สำหรับเก็บเกม Steam ที่ผู้ใช้ชอบ ระบบแบ่งเป็นหน้าจอ (UI), model, repository, service/API และ storage หลายชั้น จุดประสงค์คือให้หน้าจอไม่ต้องรู้รายละเอียดว่าเกมมาจาก Firestore, REST API หรือ SQLite

เส้นทางข้อมูลหลัก

ผู้ใช้ → Flutter page/widget → GameRepository → FavoritesApiService → Vercel API → Firestore

ข้อมูลที่โหลดสำเร็จ → SQLite cache บน Android/iOS หรือ local adapter บนเว็บ → UI

คำศัพท์ที่ควรอธิบายได้

  • State: ค่าปัจจุบันที่ทำให้ UI เปลี่ยน เช่น tab ที่เลือก, loading, รายการเกม
  • Model: รูปแบบข้อมูลหนึ่งเกมและการแปลงข้อมูลระหว่างชนิด
  • Repository: จุดรวม use case อ่าน/บันทึก/ลบ แยก UI จาก data source
  • Service: รายละเอียดสื่อสาร HTTP หรือ Firebase
  • Adapter: implementation ของ storage สำหรับ platform ต่างกัน
  • Cache: สำเนาในเครื่อง ไม่ใช่แหล่งข้อมูลหลักและไม่ใช่ offline write queue
พูดให้ตรงของจริง: การบันทึกเกมส่งผ่าน API/Cloud ก่อน แล้วจึงบันทึก cache; ถ้าออฟไลน์เปิดได้เฉพาะข้อมูลที่เคย cache ไม่ได้เพิ่ม/แก้/ลบแบบรอซิงก์ภายหลัง

02 · โครงสร้างโค้ด Flutter

ไฟล์ Dart ทำงานสัมพันธ์กันอย่างไร

1 · เริ่มแอปlib/main.dart

สร้าง widget root, เตรียม Firebase, theme, auth gate และ navigation

2 · แสดงหน้าlib/pages/

หน้า login, ฟอร์มเกม, ค้นพบเกม, ชุมชน รับ callback/constructor แล้วเรียกชั้นข้อมูล

3 · รูปแบบข้อมูลlib/models/

แปลง API JSON และ Map จาก SQLite/Firestore ให้กลายเป็น object Dart ที่ type ชัด

4 · use caselib/repositories/

กำหนดสัญญา watch/save/delete ให้ UI พึ่ง abstraction มากกว่า backend

5 · เชื่อมระบบlib/services/

ส่ง request, token, parse response, จัดการ timeout/error และประสาน Firestore

6 · เก็บสำเนาlib/data/

adapter มือถือใช้ SQLite; adapter web ใช้ storage ที่ browser รองรับ

ทำไมเปิดเกมแล้วไม่ควรเห็นหน้าดำ

ให้ตรวจว่าหน้ารายละเอียดสร้างจากข้อมูลที่มีอยู่แล้วและ render ทันที ไม่รอ network image แบบไม่มี fallback; GameArtwork จัดการ loading/error ของภาพ ส่วน async data ใช้สถานะ loading/error/empty ให้ครบ งานนี้แยกหน้ารายละเอียดของ game กับ recommended game ให้ส่ง model ผ่าน constructor

แพตเทิร์น Navigator
Navigator.push(
  context,
  MaterialPageRoute(
    builder: (_) => GameDetailPage(game: game),
  ),
);

ข้อมูลรายการถูกส่งตรงผ่าน constructor จึงไม่ต้องโหลดซ้ำเพียงเพื่อเปิดรายละเอียด

03 · State, Form และ CRUD

วงจรเพิ่ม–อ่าน–แก้–ลบ

  1. หน้า StatefulWidget เก็บค่า form/loading/filter/tab ใน State
  2. TextFormField ใช้ controller และ validator; trim ช่องข้อความก่อนสร้าง model
  3. ปุ่ม save เช็ค form ผ่านก่อน จากนั้นแสดง loading และ await repository
  4. ตอนแก้ไขส่ง model เดิมเข้า constructor ฟอร์มเพื่อเติมค่าเริ่มต้น
  5. ตอนลบแสดง dialog ยืนยันก่อนเรียก delete
  6. เมื่อบันทึกสำเร็จ ปิดฟอร์ม/รายละเอียดพร้อมผลลัพธ์ แล้ว stream/list rebuild
สิ่งที่ควรสาธิต

ปล่อยหัวข้อว่างให้เห็นข้อความเตือน → เพิ่มเกม → แตะดูรายละเอียด → แก้คะแนนหรือหมวด → ยกเลิกการลบ → ยืนยันลบ

ข้อควรจำ: setState ใช้กับ state ใน widget เท่านั้น; อย่าเรียกหลัง widget ถูก dispose (ตรวจ mounted หลัง await) และอย่าให้กดซ้ำในช่วง saving

04 · SQLite + Platform

แคชทำงานอย่างไร

GameDatabase เป็น abstraction ที่เลือก implementation ด้วย conditional import ตาม platform. Mobile ใช้ sqflite จริง ส่วนเว็บเลือก adapter Web เพราะ API/plugin ฝั่ง native ไม่พร้อมใช้เหมือนกัน

ลำดับ cache ที่ควรจำ
อ่าน: local cache ก่อน → ขอข้อมูล cloud → แทนที่ cache เมื่อสำเร็จ
เขียน: API/Cloud สำเร็จก่อน → upsert cache
ออฟไลน์: อ่าน cache ได้; เขียนไม่ถูก queue

SQL ที่ต้องอธิบายได้

  • Primary key กันแถวซ้ำ; userId ใช้ query แยกผู้ใช้
  • whereArgs ส่งค่าพารามิเตอร์แยกจาก SQL ลดปัญหา quoting/injection
  • upsert เพิ่มหรือแทนที่แถวที่ key ซ้ำ
  • boolean เก็บเป็น integer 0/1; วันที่/URL/rating เก็บชนิดที่แปลงกลับได้
ข้อมูล local เป็นของอุปกรณ์เดียวและอาจถูกล้างเมื่อลบแอป; Firestore เป็น cloud source ที่ซิงก์ข้ามเครื่อง

05 · API + Async UI

HTTP และ FutureBuilder

แอปเรียก API ผ่าน service ด้วย asynchronous Future; UI จึงไม่ค้างระหว่างรอเครือข่าย

Loading

แสดง CupertinoActivityIndicator

Success

parse JSON เป็น RecommendedGame แล้ว render list

Empty

แจ้งว่าสำเร็จแต่ไม่มีรายการ แยกจาก error

Error

ข้อความอธิบายและปุ่ม retry สร้าง Future ใหม่

REST method

  • GET อ่านข้อมูล
  • POST สร้าง
  • PUT แก้ไข
  • DELETE ลบ

API public สำหรับเกมแนะนำ/คอมเมนต์ไม่เหมือน API private สำหรับ favorites; favorites ต้องแนบ Firebase ID token ใน Authorization header และ server ต้องตรวจ request/สิทธิ์ ไม่รับ owner จาก input ของผู้ใช้มาเชื่อทันที

ก่อนอธิบายว่า production ใช้งานได้ ให้ตรวจ URL deployment, HTTP status, CORS และ deploy Rules บน Firebase project จริง อย่าโชว์ token หรือค่าลับในคลิป

06 · Auth + Security

ทำไมซ่อนรายการในหน้าแอปไม่พอ

การกรองใน UI ช่วยประสบการณ์ใช้ แต่ผู้ใช้ยังเรียก API เองได้ จึงต้องมีการยืนยันตัวตนและตรวจสิทธิ์ฝั่ง server

  1. Firebase Authentication รับผิดชอบสมัคร/ล็อกอิน/reset password
  2. หลังล็อกอินได้ UID และ ID token
  3. Flutter แนบ token เมื่อเรียก private favorites API
  4. Rules ตรวจ request.auth.uid เทียบ owner และตรวจ schema/rating
  5. การแก้ไขต้องเป็นเจ้าของทั้งเอกสารเดิมและข้อมูลใหม่; ป้องกันย้าย owner

firestore.rules ควรเป็น default-deny สำหรับ path ที่ไม่อนุญาต. Firestore Console แสดงข้อมูล แต่ Rules ต้องทดสอบใน Firebase Emulator/Console project จริงก่อนกล่าวว่า deploy แล้ว

ไฟล์ google-services.json, GoogleService-Info.plist และ firebase_options.dart คือ config client; ไม่ใช่ service-account private key. อย่าเผยแพร่ access token, password หรือ private key

07 · UX และส่วนเสริม

รายละเอียดที่ทำให้ใช้งานจริงขึ้น

  • Theme iOS: Cupertino navigation, tab bar, spacing/สีเรียบและพื้นที่แตะเหมาะกับมือถือ
  • ค้นหา/กรอง: normalize ตัวพิมพ์และเลือก genre/favorite; ใช้ผลกรองจาก list แทนแก้ข้อมูลต้นฉบับ
  • รูปเกม: loading placeholder และ fallback เมื่อ network/data image เสีย
  • เลือกรูป: gallery/camera, จัด orientation, resize/compress ก่อนเซฟ ลด payload
  • สถิติ: สรุปจำนวนเกมต่อ genre, จำนวน favorite และกราฟแท่งปรับตามค่ามากสุด
  • Animation: ใช้เฉพาะ feedback/transition ที่ช่วยบอกสถานะ ไม่ใส่จนรบกวนการอ่าน
  • Empty/error: มีข้อความเฉพาะสถานะ พร้อมวิธีทำต่อ เช่น retry

โบนัสต้องอธิบายจาก behavior ที่ทดสอบได้จริง: รูป/กล้องเป็นของเสริม, challenge features มี search, image, favorites/categories, statistics. คะแนนอาจารย์ขึ้นกับเอกสารฉบับที่กำหนดและการตรวจจริง
